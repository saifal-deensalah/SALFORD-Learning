# نتائج التحقق — 27 أغسطس 2026

## ما نُفذ فعليًا

- تثبيت dependencies وبناء TypeScript إلى `dist/` بنجاح.
- migrations فعلية على PostgreSQL مدمج عبر PGlite، مع بيانات مستمرة على القرص.
- **27 اختبارًا ناجحًا** في `test/api.test.ts`. الاختبارات ترفع Nest HTTP server حقيقيًا وتتحقق من response schemas، وليست استدعاءات شكلية للـhandlers فقط.
- استدعاء جميع **67 operation** عبر HTTP؛ التغطية في `test-results/coverage.json`.
- فحص JWT/roles/ownership، reset/verification single use، refresh replay، idempotency، عدم احتساب seek، إكمال درسين، PDF فعلي، HLS manifest وsegment فعلي، ورفض توقيع URL مزور.
- اختبار purchase verification بمزوّد محقون **داخل NODE_ENV=test فقط**، مع اختبار رفض receipts المزورة. لا يوجد endpoint لتحويل client flag إلى دفعة ناجحة.
- اختبار عدم إعادة فتح فترة ملغاة بسبب refund عند إعادة معالجة حدث active قديم، وعدم تكرار الشهادة عند retry.
- اختبار checkout مع Stripe SDK بديل داخل الاختبار: unpaid لا ينجح، ونجاح session مدفوعة لا يجعل session أخرى غير مدفوعة ناجحة. واختبار منع فتح قاعدة embedded مرتين.
- نجحت أيضًا اختبارات الفرونت إند الأصلية:27 اختبارًا، وفحص TypeScript في الجذر بعد استثناء مجلد الباك إند.
- تشغيل **النسخة المبنية** باستخدام `npm start` على localhost:3000؛ smoke أكد ready200، login200، سبع دورات، فصلًا ودرسين، unauthorized401، وSwagger200. النتائج في `test-results/runtime-smoke.json`.
- تحديث Nodemailer إلى9.0.5 بعد تقرير أمني؛ `npm audit --omit=dev` انتهى بصفر ثغرات معروفة وقت الفحص. لا يعني ذلك تدقيقًا أمنيًا شاملًا.

## ما لم يُختبر أو يُفعّل

- Google/Apple OAuth الحقيقي، شراء فعلي أو sandbox في حساب متجر حقيقي، Stripe checkout/webhook ناجح خارجي، SMTP خارجي، FCM/APNs، وS3: لا توجد مفاتيح المستخدم؛ اختُبرت حدود الرفض والإعداد، لا نجاح المزود الخارجي.
- Docker وPostgreSQL/Redis كخدمات منفصلة: ملفات التشغيل موجودة، لكن Docker غير مثبت في البيئة الحالية. اختبارات المعاملات المدمجة لا تثبت التزامن بين عدة اتصالات PostgreSQL أو الأداء تحت حمل.
- ربط React Native فعليًا بهذه APIs لم يُنفذ داخل شاشات التطبيق؛ بقي الوضع التجريبي فيه. ملف الربط يحدد تغييرات العميل المطلوبة.
- نشر production، HTTPS/DNS، حسابات المتاجر، SSO/MFA للبوابة الإدارية، backups فعلية، استعادة كوارث، ومراجعة سياسة الاحتفاظ/الخصوصية لم تُنشأ تلقائيًا.
- Offline video/DRM، PayPal adapter، بيع دورة منفردة، quizzes/chat/live classes ليست ضمن v1 المعتمد في التصميم.

## حدود تنفيذ ينبغي مراعاتها

- البحث والقوائم الحالية تجلب بيانات المجال ثم تطبق filtering/opaque cursor في الخدمة؛ مناسبة للكتالوج الأولي. قبل كتالوج كبير يجب نقل pagination/ranking إلى SQL keyset وتوسيع اختبارات الحمل.
- HLS grant مدتها5 دقائق؛ token bearer يمكن مشاركته إلى أن تنتهي المدة. S3 segments روابط قصيرة، وليس DRM. API يمنع تشغيل session جديدة بعد فقد الاشتراك.
- حد فيديو100MB مع single upload؛ multipart وفحص malware مستقل وعزل أقوى لـFFmpeg يحتاجان توسعة إذا زاد حجم المحتوى أو صار الرفع عامًا.
- PDF الافتراضي يستخدم خطًا مناسبًا للنص الإنجليزي في المحتوى الحالي. Unicode/Arabic في الشهادات يحتاج خطًا مرخّصًا عبر CERTIFICATE_FONT واختبار تشكيل واتجاه قبل التعهد بالدعم الكامل.
- توجد reconciliation لاشتراكات Stripe وعمليات checkout، لكنها لم تُختبر بمزود حي. التسويات المحاسبية وتقارير الضرائب ليست جزءًا من النظام؛ سجلات مبالغ متاجر Google/Apple لا تُستنتج من سعر الواجهة، وتقارير التسوية من المزود ضرورية للمحاسبة.
- APP_SECRET واحد حاليًا لعدة استخدامات مشتقة. لا تدوّر القيمة دون خطة لإعادة التشفير؛ key ring/versioned key rotation تحسين لازم قبل تشغيل طويل الأمد.
- ترحيلات SQL الحالية بسيطة بلا stored procedures؛ runner يقسم statements. عند إضافة دوال SQL تحتوي semicolons داخل bodies يلزم migration runner يدعمها.

هذه الحدود لا تمنع تجربة API محليًا، لكنها تمنع وصفه بأنه نشر إنتاجي كامل الخدمات تم اعتماده دون خطوات التفعيل والاختبار المذكورة.
